# design-pass — дизайн, реалізація, перевірка

Результат — інтерфейс із виразною ієрархією, завершеним основним сценарієм і доказами перевірки. Успішний білд підтверджує збірку, а не якість дизайну чи UX. Масштабуй процес до зміни: для однієї кнопки перевір її контекст і стани, для нового екрана — весь сценарій. Не розширюй невелике завдання до редизайну продукту.

## 1. Спочатку поточний проєкт

До вибору стилю чи реалізації прочитай застосовні `AGENTS.md` та `CLAUDE.md`. Знайди локальний дизайн-скіл у `.agents/skills/`, `.claude/skills/`, `skills/` або за посиланнями цих інструкцій; читай лише релевантне. Зафіксуй конкретні файли або відсутність:

- токенів кольору, типографіки, відступів і радіусів;
- наявних компонентів і layout-примітивів, які можна повторно використати;
- механізму тем і реально підтримуваних тем;
- стеку, способу стилізації, шрифтів, іконок та ресурсів;
- цільових маршрутів, команд запуску й доступних засобів перевірки.

Відсутність локального скілу **не означає**, що дизайн-осі вільні: перевір реалізацію й сусідні екрани. Не перенось Tailwind, light/dark, dark-only, палітри чи компоненти іншого проєкту в цей. Не додавай тему, шрифт або бібліотеку лише заради глобального дефолту.

## 2. Бриф, референс і план

Назви тип артефакту (`page` / `system`), аудиторію, головну задачу, межі зміни й основну дію. Визнач короткий перевірний сценарій: старт → дія → очікуваний результат; де застосовно — помилка → відновлення. Якщо даних достатньо, працюй; уточнюй лише невизначеність, що суттєво змінює результат.

- **Є референс:** прочитай [reference-ui-reconstruction](../reference-ui-reconstruction/SKILL.md). Зафіксуй viewport, межі референсу, геометрію, токени, типографіку, компоненти й невідомі. Відрізняй точне відтворення від референсу лише для настрою. Не запускай повторно цей оркестратор при зворотному посиланні зі скілу.
- **Метод:** прочитай [frontend-design](../ship/frontend-design/SKILL.md). Використай уже знайдені проєктні рішення; не повторюй пошук. Склади компактний план композиції, ієрархії, типографіки, відступів і поведінки на вузькому екрані. Назви закриті й вільні осі. Один виразний прийом або естетичний ризик доречний лише в межах брифу; для точкової правки чи відтворення не вигадуй нову стилістику.
- **Візуальний фільтр:** прочитай [anti-slop-design](../anti-slop-design/SKILL.md), оголоси design read і обґрунтуй застосовні дилси брифом. Його каталог — перевірка доречності, а не привід підмінити стиль проєкту.

Коротко запиши план і критерії приймання перед кодом. Для великої роботи використовуй прийнятий у репозиторії формат нотаток; для малої достатньо повідомлення, без додаткових файлів.

## 3. Пріоритет і межі загальних правил

Явний запит користувача визначає мету. Для візуальних рішень: **авторитетний референс > проєкт > метод > generic-дефолти**. Проєкт визначає спосіб реалізації; референс не є дозволом замінити стек. Конфлікт референсу з канонічною системою назви й зафіксуй потрібне відхилення, не переписуй глобальні токени мовчки.

У цьому процесі правила допоміжних скілів про конкретні шрифти, кількість акцентів, теми, радіуси, пунктуацію, бібліотеки іконок, CSS-класи чи обов'язковий моушн — умовні евристики. Не роби їх універсальними блокерами. Поясни доречний виняток; не міняй бренд, текст або семантичні кольори станів заради механічного чекбокса. Загальні патерни UX також застосовуй до задачі, а не як наказ завжди додавати sidebar, модалку чи розбивати форму.

Водночас вигляд референсу або правило проєкту не доводять доступність чи працездатність. Виявлену проблему не позначай як `pass` лише через її походження. Не вигадуй відгуки, клієнтів, метрики чи успішні перевірки.

## 4. Реалізуй завершений зріз

Спершу структура й геометрія, потім типографіка, контент, компоненти та деталі. Повторно використовуй токени і примітиви. Копірайт і реалістичні довжини тексту — частина дизайну; для текстів застосуй ресурс `WRITING.md` зі скілу frontend-design. Демо-дані позначай як демо.

До здачі забезпеч і перевір застосовні критерії:

| Вісь | Спостережуваний результат |
| --- | --- |
| Ієрархія | Видно призначення екрана й основну дію; вторинні дії не конкурують; заголовки, групування, вирівнювання та ритм відступів узгоджені. Немає обрізаного тексту, випадкових переносів або декору без функції. |
| Адаптивність | Desktop і вузький екран зберігають зміст, порядок і доступність дій. Навігація, таблиці, модалки й sticky-елементи мають явну поведінку; немає випадкового горизонтального overflow. Перевір також проміжну ширину біля зміненого breakpoint. |
| Стани | Для змінених контролів: rest, hover де є pointer, pressed/selected, видимий focus, disabled і pending де застосовні. Для даних/форм: loading, empty/no-results, error з відновленням, success. Не додавай неіснуючий асинхронний стан до статичного контенту. |
| Доступність | Семантичні заголовки й контроли, доступні назви та підписи, alt за змістом, логічний порядок клавіатури, видимий неперекритий фокус. Для діалогу — вхід, закриття й повернення фокуса. Перевір контраст вимірюванням, а не враженням; стан не передається лише кольором. |
| Сценарій | Головна дія виконує обіцяне й дає зворотний зв'язок; назад/скасування працює, помилка не стирає введене. Пройди головний шлях і релевантний шлях помилки/повтору. Довгий текст, порожні й переповнені дані не руйнують екран. |
| Рух і масштаб | Якщо є анімація, вона пояснює дію/стан, не заважає та поважає reduced motion. Окремо перевір збільшення тексту до 200% і reflow на вузькому viewport; одне не зараховуй за інше. |

Це базова перевірка зміненого UI, не сертифікація WCAG. Для конкретних критеріїв та джерел використовуй застосовні розділи [правил ux-review](../ux-review/references/rules.md), враховуй рівень відповідності й винятки. Не оголошуй повну відповідність за скріншотом або одним автоматичним сканом.

## 5. Браузер → знахідки → виправлення → повторна перевірка

Перед проходом склади компактний inventory нових/змінених UI states у чинному plan/report. Якщо в scope є popover, active trigger чи chips, потрібне явне visual coverage кожного з цих станів; closed/default screenshot їх не доводить. Незастосовне познач N/A з причиною, потрібне, але недоступне — BLOCKED.

1. **Визнач можливості.** Використай реально доступний браузерний інструмент, локальний тестовий runner чи засоби проєкту. Не припускай наявність конкретного MCP, Playwright, браузера або image viewer. Знайди документовану команду запуску; не встановлюй новий стек перевірок лише заради цього скілу.
2. **Відкрий результат.** Запусти чи використай локальний застосунок, відкрий змінений маршрут із відтворюваними даними. Для редизайну, коли можливо, зніми стан до зміни. Перевір завантаження шрифтів/ресурсів і пов'язані runtime-помилки.
3. **Подивись і взаємодій.** Зніми та реально переглянь desktop і mobile скріншоти (точні розміри запиши; наприклад 1440×900 і 390×844, якщо проєкт не задає інші). Оглянь також контент нижче першого екрана. Пройди сценарій, клавіатуру, стани й масштаб із §4. Статичний скрін не підтверджує поведінку, а створений, але не переглянутий файл не підтверджує візуальну якість.
4. **Порівняй.** Для референсу — той самий viewport і стан, side-by-side/overlay/diff за доступністю. Без референсу — проти плану, критеріїв і системи проєкту. Спочатку великі пропорції та ієрархія, потім типографіка, відступи й деталі.
   Відокрем фактичний diff, пояснення його причини та рішення прийняти baseline. Малий відсоток diff не доводить відсутності регресії; у modal перевір foreground і background/backdrop. Не проголошуй no-diff без фактичного порівняння. Не оновлюй baseline сліпо: збережи погоджений локальний механізм review та докази відмінностей.
5. **Виправ і перевір знову.** Запиши конкретний дефект, місце й доказ; виправ у межах задачі. Повтори той самий сценарій/viewport та зачеплені сусідні стани. Після фінальної правки потрібні свіжі докази: скрін до виправлення не підтверджує виправлення. Повторюй, поки критерії виконані або з'явився конкретний блокер; не крути косметичні варіанти без критерію покращення.

Для фінального проходу застосуй [interface-review](../interface-review/SKILL.md): візуальна й UX-лінзи обов'язкові для зміненого UI, але глибина відповідає скоупу. Повторно використовуй зібрані докази, дедуплікуй знахідки. Це етап виправлення в design-pass, не лише звіт аудиту.

Якщо інструмент, запуск, дані або доступ заблоковані, виконай доступні незалежні перевірки й назви точну причину та наступний крок. Статичний аналіз, білд і тести звітуй окремо від браузера. Відсутня можливість перегляду не скасовує зроблену реалізацію, але залишає візуальну перевірку заблокованою.

## 6. Done і передача

«Готово й перевірено» лише коли для погодженого скоупу:

- проєктні обмеження, план і застосовні критерії зафіксовані;
- реалізація проходить доречні перевірки проєкту;
- актуальний результат переглянутий у браузері на desktop/mobile, основний сценарій і застосовні стани перевірені;
- референс, якщо був, порівняний у цільовому viewport; відмінності описані;
- застосовний pre-flight anti-slop та UX-прохід виконані; blocker/major виправлені й переперевірені. Виняток — лише явно прийняте користувачем обмеження з датою та впливом, статус «готово з обмеженнями». Сам факт запису дефекту не є його прийняттям.

Наприкінці коротко повідом: що змінилося і чому; які екрани/сценарії/viewport перевірено; де докази; що залишилось. Для перевірок використовуй **PASS / FAIL / BLOCKED / N/A** з підставою. Неперевірене не є PASS; для N/A поясни незастосовність. Якщо ключова перевірка заблокована, статус — «реалізовано, перевірка неповна», з конкретним наступним кроком замість безумовного «готово».

Звір summary і plan checklist з evidence саме фінальної revision/diff: старий PASS не закриває нову UI delta. Якщо acceptance вимагає keyboard action, перевір потрібну клавішу browser input і очікуваний UI-effect; це simulated browser key, не фізична ручна QA і не unit dispatch submit. Завершений task не перевиконується лише через ідентичний handoff за незмінених inputs; не приписуй повтор автоматизації без доказів.

## Використання в терміналі

Спільний `SKILL.md` не потребує особливих інструментів конкретного агента:

- **Codex CLI:** `$design-pass` у запиті або вибір через `/skills`.
- **Claude Code:** `/design-pass` із завданням після команди.

Наприклад: «Онови екран налаштувань у поточному проєкті. Спершу знайди токени й примітиви; реалізуй і перевір основний сценарій, адаптивність та стани в браузері. Виправ знайдене, покажи докази й окремо назви заблоковані перевірки».

Посилання на допоміжні скіли відкривай як файли відносно цієї папки, не припускай доступності slash-команди чи спеціального tool. Якщо ресурс відсутній — назви його, продовжуй за доступними вимогами цього скілу й не зараховуй невиконаний спеціалізований гейт.

## Browser evidence refinement

For permission/session/error recovery states and action-correlated DOM, console or network evidence, use [browser state evidence](references/browser-state-evidence.md). Reuse the existing entity coverage and reviewer route; this adds no tool installation or second checklist.
